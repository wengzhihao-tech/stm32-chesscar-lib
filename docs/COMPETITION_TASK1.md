## 一、先说最重要的结论：这不是循迹赛

初版代码库是按"光电循迹小车"准备的。读完赛题后必须纠正：

| | 循迹赛 | **本赛题** |
|---|---|---|
| 引导线 | 有，车跟线走 | **没有**，3m×2m 开放场地 |
| 核心难点 | 跟线稳定性 | **自主定位 + 目标识别 + 决策** |
| 外环控制 | 探头偏差 → 差速 | **坐标导航** → 差速 |
| 对抗性 | 无 | 有，且禁止恶意冲撞 |

**`line_follow`（循迹外环）在本赛题用不上。** 已保留在库中（换回循迹练习时仍可用），
但比赛主线改由 `navigator`（点到点导航）+ `match_fsm`（比赛状态机）驱动。
`line_sensor` 可降级用于边界/压线检测。

## 二、赛题硬约束与代码位置

全部常量集中在 `common/field_config.h`，不要散落在各处。

| 赛题要求 | 代码位置 |
|---|---|
| 场地 3m×2m，四周 80mm 挡板 | `FIELD_LENGTH_CM` / `FIELD_WIDTH_CM` / `FIELD_WALL_HEIGHT_MM` |
| 车≤250×200×180mm，≤1.5kg | `CAR_MAX_*`（见下方重量预算） |
| 激光 ≤1mW，II 类 | `CAR_MAX_LASER_POWER_MW` —— **超标直接判负，见红线清单** |
| 32 枚棋子，红黑各 16，1-10 分 | `CHESS_PIECE_*` / `Chess_LevelScore()` |
| 推棋子**整体**进己方球门得分 | `Chess_IsInOurGoal()`，按棋子半径内缩判定 |
| 禁止恶意冲撞对方车辆 | `Navigator_Update()` 的对手规避分支 |
| 禁止电磁铁吸附 | 推板/滚轮方案，见机构选型 |
| 全程全自主，禁止人工干预 | `match_fsm` 全自动流转，无人工介入点 |
| 平局比进球总数、"帅/将"归属 | `ourGoalCount` / `ourGeneralScored` |

### ⚠ 必须现场确认的参数

赛题图1 明确备注**"尺寸后续由主办方根据场地要求进行修订"**，所以：

- **球门区尺寸未公布**：`FIELD_GOAL_DEPTH_CM_ESTIMATED`、`FIELD_GOAL_WIDTH_CM_ESTIMATED`
  是按示意图比例的**估算占位值**，拿到正式场地图必须替换，否则进球判定位置会错。
- **棋子分值表未公布**：赛题只说"按等级设置 1-10 分"，没给对应表。
  `Chess_LevelScore()` 里是按象棋常规强弱的假定值，拿到正式计分表后更新。
- **比赛总时长未给出**：只提到平局有 60 秒金球加赛。
  `matchDurationMs` 按 3 分钟占位，须按现场规则手册修改。
- **发车区位置**：取决于抽签（甲队/乙队），开赛前设置 `FIELD_OUR_SIDE`。

└───────────────┬─────────────────────────────┘
                │ 串口 CRC16 帧 (0x14 棋子上报)
┌───────────────▼─────────────────────────────┐
│ STM32F407  主控                              │
│                                              │
│  ┌── 20ms 决策/导航层 ──────────────┐        │
│  │ match_fsm   比赛状态机            │        │
│  │ chess_target 选哪枚最划算          │        │
│  │ navigator   点到点导航 + 避障      │        │
│  └──────────┬───────────────────────┘        │
│  ┌── 10ms 运动控制层 ────────────────┐       │
│  │ speed_control 双轮速度闭环 (PI)    │       │
│  │ pid_controller 抗积分饱和          │       │
│  └──────────┬───────────────────────┘        │
│  ┌── 位姿估计（基础） ────────────────┐      │
│  │ pose_estimator 里程计+IMU+贴边校正 │      │
│  └───────────────────────────────────┘      │
└──────────────────────────────────────────────┘
    │ TB6612      │ 编码器      │ ToF×4   │ IMU

**为什么双主控**：图像处理在 STM32F4 上做不动，运动控制需要硬实时的 10ms 节拍，
视觉板跑 Python 保证不了实时性。各做擅长的事，用 CRC16 帧协议解耦。

## 四、定位方案：本赛题最大难点

开放场地里车必须自己知道身在何处。三级融合，缺一不可：

### 第 1 级：差速里程计（`pose_estimator.c`）
编码器积分出 (x, y, θ)。短时间很准，但**轮子打滑的误差永远无法恢复**。

用了"中点航向"积分（二阶精度）而不是用更新前的航向——车在一个周期内是边转边走的，
取中点能显著降低转弯时的位置误差。

### 第 2 级：IMU 航向替换
陀螺积分的航向不受轮子打滑影响，短期优于轮式里程计，用它替换里程计的 θ。
但陀螺有零偏，长时间同样会漂。

> 博世原厂 FAE 回复：BMI088 陀螺零偏不稳定度未写入数据手册，实际 **< 2 °/hour**；
> 轴间交叉灵敏度 ±1%，对应约 ±0.57° 安装失准。
> <https://community.bosch-sensortec.com/mems-sensors-forum-jrmujtaw/post/bmi088-bias-instability-and-alignment-errors-not-specified-in-the-datasheet-UswQwo3Gr0OwqxD>

### 第 3 级：挡板绝对校正（**关键，不能省**）
场地四周 80mm 挡板是唯一稳定的绝对基准。车贴近某面挡板时，
用 ToF 侧向测距把该轴坐标直接"钉"回绝对值，一次清掉前面累积的全部漂移。

**为什么必须有第 3 级**：纯里程计在场地里跑两三分钟，位置误差很容易到十几厘米。
那时候"把棋子推进球门"就变成"把棋子推到球门外面"。

`PoseEstimator_CorrectByWall()` 刻意设计了两道拒绝门限（不是缺陷）：
- 测距超 40cm 拒绝 —— 可能测到的是对方车或棋子堆，不是挡板
- 航向与挡板法线夹角 >12° 拒绝 —— 斜着测得到的是斜边，不等于垂直距离

### 激光雷达要不要上？

调研到的第三方方案报告给出了一个关键判断：
**把雷达扫描面放在 50mm 高度，能看见 80mm 挡板、对方车和门框立柱，
但看不见约 10mm 厚的棋子**，挡板是最可靠的定位基准。
<https://blog.csdn.net/xiegao614/article/details/166597442>

这意味着：
- 雷达**能**解决定位（扫挡板轮廓做匹配），比纯 ToF 贴边更鲁棒
- 雷达**不能**解决棋子识别 —— 棋子太薄，扫不到。棋子必须靠视觉

参考规格（第三方整合，非官方手册）：

| 型号 | 量程 | 频率 | 精度 | 尺寸/重量 | 价格 | 来源 |
|---|---|---|---|---|---|---|
| LDROBOT LD19/STL-19P | 0.02–12m | 10Hz, 4500点/s | — | 47g | ≈150元 | [CSDN 方案报告](https://blog.csdn.net/xiegao614/article/details/166597442) |
| RPLIDAR C1 | 12m | 8/12Hz | ±3cm | 55.6×55.6×41.3mm | — | [Hiwonder](https://www.hiwonder.com/products/lidar-a1-a2) |
| RPLIDAR A1 | 0.15–12m | 5.5Hz | 3m内1%量程 | 96.8×70.3×55mm | — | [Hiwonder](https://www.hiwonder.com/products/lidar-a1-a2) |

> **注意 RPLIDAR A1 的 0.15m 最小量程**：在 3m×2m 小场地里，车贴近挡板时
> 挡板会进入盲区。LD19 的 0.02m 起测更适合小场地。
> A1 尺寸 96.8×70.3mm 也明显大于 C1 和 LD19，在 250×200mm 车体上占比不小。

**建议**：先用 4 路 ToF 贴边校正（成本低、重量轻、代码已就位）跑通全流程；
若预算和时间允许，再加 LD19 做挡板轮廓匹配提升鲁棒性。

## 五、棋子识别：必须认清能力边界

棋子约 Φ32mm × 厚 9mm，红黑两色，表面有汉字。

| 任务 | 可行性 | 说明 |
|---|---|---|
| 红黑颜色区分 | **可靠** | 对比强烈，颜色阈值即可 |
| 圆形轮廓定位 | **较可靠** | 典型误差 2~3cm，距离越远越斜越差 |
| 汉字等级识别（帅/将/车/马/炮…） | **不可靠** | 低分辨率+斜视角+运动模糊下极难稳定 |

**因此代码策略是"等级允许未知"**：`Chess_LevelScore(CHESS_LEVEL_UNKNOWN)` 返回
保守中间值 4，车不会因为读不出汉字就放弃棋子——毕竟推进球门就有分。
若你们最终做出了可靠的汉字识别，直接在协议 payload 里填真实等级，决策层无需改动。

### ToF 能识别棋子吗？不能

VL53L1X 接收 FoV 可在 15°~27° 编程（[ST 官方手册](https://www.st.com/resource/en/datasheet/vl53l1x.pdf)）。
在 40cm 处 FoV 15° 对应的光斑直径约 10cm，**比 Φ3.2cm 的棋子大得多**，
测到的是区域平均距离，无法分辨单枚棋子。ToF 只能测挡板和车辆这类大目标。

### 相机安装：俯视 vs 前视

- **俯视**（推荐）：做一次四点透视变换就能把像素映射到场地坐标，
  STM32 侧不需要知道任何相机参数。缺点是受 180mm 限高约束，视野有限。
- **前视**：视野远，但像素→场地坐标需要已知车辆位姿，定位误差会耦合进识别误差。

### ⚠ 多路 ToF 的 I2C 地址冲突（必踩的坑）

所有 VL53L0X 出厂地址都是 **0x29**，挂同一条 I2C 必须改址，否则完全读不出数据。

**改址流程**（`Tof_Init()` 已实现，顺序不能错）：
1. 把**所有** XSHUT 拉低（全部关断）—— 这步不能省，否则改址会同时命中多个模块
2. 逐个拉高一个模块的 XSHUT，等约 5ms 启动
3. 立即用 0x29 与它通信，写寄存器 0x8A 改成目标地址（如 0x30/0x31/0x32/0x33）
4. 保持该模块上电，再处理下一个

**关键：改址后断电不保留，每次上电都要重跑整个流程。**
参考：<https://forum.seeedstudio.com/t/how-to-change-i2c-address-on-grove-time-of-flight-distance-sensor-vl53l0x/266866>

### 尺寸预算（上限 250×200×180mm，发车状态）

- 180mm 限高对俯视相机是硬约束：相机越低视野越小。
- 推板若是可展开结构，**发车状态必须收在 250×200mm 内**（赛题写的是"发车状态尺寸"）。
  这点要和裁判确认：展开后是否允许超出。

### 推板/收集机构

赛题允许推板、滚轮，**禁止电磁铁吸附**。

- 舵机推板最简单可靠。SG90（约 9g，扭矩约 1.8kg·cm）够推几枚轻棋子；
  MG996R（约 55g，扭矩约 9~11kg·cm）力量充裕但偏重。
  *这两个型号的扭矩/重量为常见公开标称值，本次未取得官方手册原文，下单前请核对实物规格书。*
- 推板宽度直接决定 `pushLostDistanceCm`（推丢判定阈值）。板越宽容错越大，
  但受 200mm 车宽限制。建议先做 120~150mm 宽的直板跑通流程。

## 七、规则红线清单（违反直接判负或扣分）

| 红线 | 赛题原文 | 工程措施 |
|---|---|---|
| **激光功率 >1mW** | "激光功率超标…将被扣分或直接判负" | 只用成品 II 类激光模块并留存规格书；**不要自己调驱动电流**；赛前用功率计实测留证 |
| **恶意冲撞对方车辆** | "恶意冲撞对方车辆…扣分或直接判负" | `Navigator_Update()` 中对手距离 <35cm 立即停止前进并转开，优先级高于任何导航目标 |
| **电磁铁吸附** | "禁止电磁铁吸附" | 只用推板/滚轮等机械推进 |
| **遥控操作/人工干预** | "全程全自主运行，禁止场外遥控与人工干预" | `match_fsm` 全自动；**比赛时关闭所有调参通道**（`PID_TUNE` 消息须在比赛固件中禁用，详见下方） |
| **破坏性装置** | "禁止…破坏性装置" | 推板边缘倒圆，不加任何尖锐或夹持结构 |

> **特别注意调参通道**：库里的串口 `PID_TUNE`(0x30) 消息在调试期很好用，
> 但它本质上是一个"场外可改变车辆行为"的通道。
> **比赛固件必须用编译开关关掉接收端处理**，避免被认定为遥控操作。
> 这是一个容易被忽略的合规风险。

### 新增模块（本赛题专用）

| `common/vision_chess.*` | 视觉棋子上报解析（协议 0x14） |
| `stm32/tof_vl53l0x.*` | 多路 ToF 管理，含 I2C 改址流程 |

### 决策逻辑：不是"推最近的"

`Chess_SelectBestTarget()` 的代价函数：

```
cost = 接近距离 + 推送距离 × 权重(默认2.0) − 分值 × 权重(默认10) + 风险惩罚
```

- **推送距离权重高于接近距离**：推着棋子走远路既慢又容易推偏，比空载移动代价高
- **风险惩罚**：贴墙棋子车可能没空间站到它背后；离对方球门近的棋子容易被反抢

### 推送几何：必须站到棋子背后

`Chess_ComputeApproachPoint()` 算的是"从球门指向棋子，再往外延伸 standoff"的点。
**直接冲到棋子位置只会把它撞偏甚至撞出场。** 车必须先到棋子背向球门的一侧，
车头朝球门，才能把它直线推进门。

## 九、备赛建议顺序

1. **先确认规则细节**（最高优先）：向主办方/裁判确认球门区尺寸、棋子分值表、
   比赛时长、推板展开是否允许超出发车尺寸。这些直接决定代码常量和机构设计。
2. **台架标定运动层**：按 `docs/TUNING_GUIDE.md` 走完死区→前馈→速度环。
   这步不过关，后面全是空谈。
3. **位姿验证**：手推车走一个 1m×1m 方形回到原点，看 `pose_estimator` 的闭合误差。
   误差 >10cm 就先查轮径/轮距/IMU 方向，不要急着上决策。
4. **贴边校正验证**：确认 `wallCorrectionCount` 在跑动中确实在增长。
   **如果一直是 0，说明校正从未生效**，位姿必然会漂。
5. **视觉标定**：俯视四点透视变换，验证上报坐标与实测位置误差 <3cm。
6. **单枚棋子闭环**：场上只放一枚棋子，跑通"搜索→接近→对准→推送→进门"。
7. **多枚 + 对抗**：加棋子，再和另一辆车对练，重点验证规避逻辑不会误判。

## 十、已知缺口（如实说明）

- **硬件层未在实物 STM32 上验证**。全部 17 个编译单元零警告通过，
  算法层 136 项断言通过，但引脚分配、编码器方向、ToF 改址流程、
  I2C 时序都必须现场实测确认。
- **`tof_vl53l0x.c` 是简化实现**。它做的是多传感器组织、地址分配与读数过滤；
  完整的校准、SPAD 管理、长距模式配置请引入 **ST 官方 VL53L0X/VL53L1X ULD 驱动**，
  把 `Tof_ReadRangeMm()` 换成官方 API 即可，上层逻辑不用改。
- **未实现激光系统控制**。赛题允许 ≤1mW II 类激光但没说明它在计分中的作用，
  需确认用途（瞄准指示？目标标记？）后再设计。
- **未实现雷达 SLAM**。当前定位靠 ToF 贴边校正。若决定上 LD19，
  需新增扫描匹配模块，`pose_estimator` 已预留了校正接口可以接入。
- **IMU 驱动未包含**。`pose_estimator` 接收的是已算好的航向角，
  具体 IMU 的寄存器读取与姿态融合需按选定型号补充。
- 舵机 SG90/MG996R 的扭矩与重量采用常见公开标称值，本次未取得官方手册原文。
